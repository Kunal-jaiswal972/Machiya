# Data model

**Read this when** you are touching `schema.prisma`, writing a migration, or
changing a geo query.

Source: [`packages/db/prisma/schema.prisma`](../packages/db/prisma/schema.prisma).
Every line of raw SQL in the repo lives in
[`packages/db/src/geo-queries.ts`](../packages/db/src/geo-queries.ts).

## The PostGIS invariant

This is the rule to internalise before anything else.

Prisma cannot `SELECT` an `Unsupported("geography(Point, 4326)")` column. So
every geo model stores **both**:

- `lat` and `lng` as plain `Float`s — what the API reads and returns;
- `location geography(Point, 4326)` — what PostGIS indexes and queries.

The two must never disagree, and the invariant is enforced **in the database, by
a trigger**, never in application code:

```sql
CREATE TRIGGER listing_sync_location
  BEFORE INSERT OR UPDATE OF lat, lng ON "Listing"
  FOR EACH ROW EXECUTE FUNCTION machiya_sync_location();
```

The alternative — a Prisma transaction that inserts the row and then issues a
raw `UPDATE ... SET location = ST_MakePoint(...)` — puts the invariant in
application code, which means the seed, an admin tool, a bulk import and a manual
`psql` fix all have to remember it. A trigger makes it impossible to skip and
keeps a write to one statement (D2).

Three models carry it: `Listing`, `OfficeLocation`, `Locality`. Adding a fourth
means adding a trigger, a CHECK and a GiST index in the migration.

### Why `location` is nullable in the schema

It is not nullable in reality. Declaring an `Unsupported()` field REQUIRED makes
Prisma **drop the model's `create` operation entirely** —
`prisma.listing.create()` then fails at runtime with "Operation 'createOne' for
model 'Listing' does not match any query", leaving no way to write a listing
through the client at all.

So the column is optional in `schema.prisma` and the real invariant is a CHECK
constraint added in the hand-written migration:

```sql
ALTER TABLE "Listing"
  ADD CONSTRAINT listing_location_present CHECK ("location" IS NOT NULL);
```

Prisma has no CHECK support, so it ignores these and reports no drift. Between
the BEFORE trigger and the CHECK, a row with a null location cannot exist — and a
test proves the constraint fires when the column is nulled behind the trigger's
back (D15).

## What is in the schema versus hand-written

| Thing                              | Where                           | Why                                                                                                                 |
| ---------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GiST indexes on `location`         | `schema.prisma`                 | Prisma emits them, and introspects them — leaving them hand-written meant every `migrate dev` produced a DROP (D13) |
| GIN trigram indexes                | `schema.prisma`                 | Same, via `@@index([name(ops: raw("gin_trgm_ops"))], type: Gin)`                                                    |
| The sync trigger                   | hand-written migration          | Not expressible in Prisma                                                                                           |
| CHECK constraints                  | hand-written migration          | Not expressible in Prisma                                                                                           |
| The partial index on PUBLISHED     | hand-written migration          | Not expressible in Prisma                                                                                           |
| `postgis` and `pg_trgm` extensions | plain SQL in the init migration | The `postgresqlExtensions` preview feature is gone in Prisma 7 (D5)                                                 |

`scripts/postgres-init/zz-prisma-owns-extensions.sql` drops the extensions the
`postgis/postgis` image installs automatically, so Prisma's migration history is
the only thing that creates them. Without it, a completely fresh clone reports
drift and demands a reset before the first migration can be written (D16).

## Models

Grouped by what they are for.

**Reference** — `City` (slug, centroid, bbox, transit fares, default fuel),
`Locality` (named neighbourhoods, queried by the autocomplete's local tier),
`Amenity`.

**Identity** — `User` (role: `SEEKER` / `LISTER` / `ADMIN`, plus the Better Auth
ban trio), and the three Better Auth models `Session`, `Account`, `Verification`.
Those three are generated by `pnpm auth:generate` and verified by
`pnpm auth:check`; see [auth.md](auth.md).

**Listings** — `Listing`, `ListingImage`, `ListingAmenity`, `ListingView`.

**Engagement** — `Enquiry` (one thread per seeker per listing, enforced by a
unique index), `EnquiryMessage`, `Favorite`, `SavedSearch`, `OfficeLocation`.

**Prices** — `FuelPrice`, keyed `(cityId, fuelType, fetchedAt)` so a re-scrape
within the same period upserts rather than inserting a near-duplicate.

### Money

`rentAmount`, `salePrice`, `securityDeposit` and `maintenanceMonthly` are `Int`
holding **whole rupees**. No sub-rupee rent exists in this market, and `Int`
keeps the money out of `Decimal` serialisation — which would otherwise leak a
Decimal instance into every JSON response and every arithmetic expression in the
commute-cost engine.

`FuelPrice.price` is the exception: `Decimal(8, 2)`, because petrol is quoted to
the paisa and rounding it would visibly skew a monthly commute cost (D17).

### `ListingImage.variantBaseKey`

Where an image's public variants live, without the `/{size}.{ext}` tail. An
upload gets `variants/{listingId}/{imageId}`; a shared seed photo gets
`variants/fixtures/{photoId}`. It is stored rather than recomputed so one photo
can serve many listings, and so the URL for an image has one source of truth. See
[images.md](images.md) and D41.

### Enum duplication, and the guard against drift

The Zod enums live in `packages/shared/src/enums.ts` and are **not** derived from
Prisma — deriving them would mean `shared` importing `@machiya/db`, which already
imports `shared`.

Instead `packages/db/src/enum-guard.ts` holds a type-level `Exact<A, B>`
assertion per enum against the generated Prisma types. Add a variant to one side
only and `pnpm typecheck` fails on that file, naming the enum. One source of
truth for validation, no cycle, and the duplication cannot rot silently (D14).

## Query rules

Everything in `geo-queries.ts` obeys these without exception:

1. **Coordinates, radii and filter values are bound parameters.** Nothing is
   interpolated into SQL text. `Prisma.raw` appears only for sort directions and
   comparison operators chosen from a closed `switch`.
2. **Filters compose into one statement.** Nothing fetches a superset and filters
   it in JavaScript.
3. **Inputs are Zod-validated going in, rows Zod-parsed coming out.**
4. **Keyset pagination, never `OFFSET`.** Cursors carry `(sortKey, id)`
   base64url-encoded, and the secondary sort always runs in the same direction as
   the primary so the row-constructor comparison stays correct for descending
   sorts. `OFFSET` would skip or repeat rows while listings are published
   underneath a paging user, and gets slower with every page (D19).
5. **KNN is always bounded.** `ORDER BY location <-> subject` alone has no notion
   of "too far": once local matches run out, a listing 1,500 km away is a
   perfectly good nearest neighbour, and a test caught exactly that.
   `findSimilarListings` applies `ST_DWithin` (default 10 km) before the KNN
   ordering so the operator still drives an index-assisted scan (D18).

One Prisma 7 gotcha worth knowing: the driver adapter infers bound parameter
types differently from the old Rust engine, so a float multiplied against an
`Int` column needs an explicit `::double precision` cast or Postgres rejects it
with `invalid input syntax for type integer` (D5).

## Commands

```bash
pnpm db:deploy      # apply migrations (no drift check — use for setup)
pnpm db:migrate     # create a migration from a schema change
pnpm db:seed        # re-seed; idempotent, prunes listings no longer planned
pnpm db:reset       # drop, re-migrate, re-seed
pnpm db:studio      # browse the data
pnpm -F @machiya/db test    # geo queries against real PostGIS
```

Every Prisma command runs **from the repo root** with an explicit `--schema`
path, so the root `.env` is the single source of environment truth (D4). The
connection string lives in `prisma.config.ts`, not in the schema (D5).

`prisma migrate reset` refuses to run when it detects an AI agent and requires an
explicit consent variable naming the user's own words. That is deliberate on
Prisma's part; if you hit it, ask.

To rebuild a local database without `reset` at all:

```bash
docker compose exec postgis psql -U machiya -d machiya \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
docker compose exec -T postgis psql -U machiya -d machiya \
  < scripts/postgres-init/zz-prisma-owns-extensions.sql
pnpm db:deploy && pnpm db:seed
```

## The seed

`packages/db/prisma/seed.ts` guarantees two properties, both load-bearing:

- **Idempotent.** Everything upserts on a stable slug or composite key, and
  `seedListings` finishes by deleting any listing of the seed lister's whose slug
  is not in the current plan — upsert-by-slug alone is not idempotent across a
  change to the _plan_, and re-seeding after adjusting the layout once turned 51
  listings into 90 (D29).
- **Deterministic.** All randomness comes from a fixed-seed mulberry32 PRNG, so
  the same listings land at the same coordinates with the same prices on every
  machine. That is what makes screenshots and bug reports comparable.

Listings cluster ~65% on the first two localities of each city, where the dev
offices are, rather than spreading evenly: an even spread left only three to
seven listings inside a 3 km radius, which is the one view the entire product is
built around (D30).
