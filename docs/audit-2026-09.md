Moved to Prisma 7.10.0 rather than pinning back: `prisma.config.ts` at the root
carries the schema path, the migrations path and the connection string;
`@prisma/adapter-pg` supplies the connection in `packages/db/src/client.ts`;
`copy-runtime.mjs` is deleted because there is no engine binary to carry any
more. D5 rewritten with the full list, D3 and D7 adjusted so they no longer
contradict it.

Verified: `pnpm db:validate`, `pnpm db:generate`, `pnpm db:migrate` ("Already in
sync"), `pnpm db:reset` (with the consent variable the v7 CLI now demands of an
AI agent), `pnpm db:seed` (51 listings, 9 fuel rows), a live query through the
adapter (`similarity('Koramangala','koramangla')` = 0.643), `pnpm build`,
`pnpm typecheck`, `pnpm lint`, `pnpm test` (107 tests), and
`docker build -f apps/api/Dockerfile` end to end.

Two things the upgrade actually broke, both now fixed rather than silenced:

- the driver adapter's parameter typing made
  `s."price" * (1 - $n)` infer `$n` as `integer`
  (`invalid input syntax for type integer: "0.25"`), failing two
  `findSimilarListings` tests. Fixed with an explicit
  `::double precision` cast, not a schema change.
- both test global-setups ran `prisma migrate deploy` from `packages/db`, where
  v7 cannot find the root config: "The datasource.url property is required in
  your Prisma config file". They now run from the repo root.

`pnpm typecheck` also grew to cover `prisma.config.ts` and `scripts/` through the
new `tsconfig.tools.json` — root-level TypeScript that no workspace package
owned, and therefore the one part of the tree nothing was checking.

## Step 0 — audit of what step 7 built

verdict below is about the code as step 7 left it. Every line was checked

### Where does the Overpass URL enter the code?

**One env var, behind the adapter. The swap is cheap.**

`grep -rn OVERPASS apps packages scripts docker-compose.yml .env.example`
returns nine hits and no others: the `OVERPASS_URL` / `OVERPASS_TIMEOUT_MS`
declarations in [apps/api/src/env.ts](../apps/api/src/env.ts#L92-L100), the two
uses inside [apps/api/src/geo/overpass.ts](../apps/api/src/geo/overpass.ts)
(the `fetch` target and the `[timeout:]` in the query), the compose
passthrough, and two `.env.example` lines. No feature code, no test and no
second call site mentions a mirror.

The 429/504 handling is inside the adapter too, in one place: `fetchPois`
throws on those two statuses and `warm` catches everything and logs. Nothing
above the adapter knows a rate limit exists — callers see `degraded: true` and
an empty or stale list. So pointing `OVERPASS_URL` at a local service is a
one-line change plus deleting the politeness reasoning.

One more Redis key exists — `view:{listingId}:{viewerHash}`
(`services/listing-detail.ts:160`) — and it is deliberately **not** in that

**A finding while writing them down:** the POI key does not include the
requested categories, while `PoiProvider.nearby` accepts a `categories` subset.
Today the only caller (`getListingPois`) passes none and gets all seven, so
nothing is wrong in practice — but a future caller asking for two categories
would poison the full-set entry. 7A adds the category set to the key.

### Real interfaces, or an inlined Overpass client?

**Real interfaces.** `packages/shared/src/geo/providers.ts` declares
`GeocodeProvider`, `RoutingProvider` and `PoiProvider` with Zod result schemas
and imports nothing about any concrete service; the clients live in
`apps/api/src/geo/` behind `resolveGeocodeProvider()`, `resolveRoutingProvider()`
and `resolvePoiProvider()`. Nothing to fix here — the interfaces were built in
correction 2, part 2.

### Does anything assume planet-current OSM?

**Yes, and only the POIs.** Routing and geocoding already read the fixed extract
(`osm-data/merged.osm.pbf`, cut on 2026-09-02); the POI panel was the one
surface reading live planet data through a public mirror. Two concrete
consequences:

- Every POI number in the step 7 section above — 343 elements, Proteeth Dental
  at 230 m, MedPlus at 180 m, Chinmaya Vidyalaya at 260 m — was measured
  against planet-current data and **is not evidence about the extract**. It is
  re-verified after the rebuild, later in this document.
- A listing's road graph and its nearby-hospital list could disagree about what
  exists. That is unfalsifiable in a bug report, and it is the substantive
  reason for correction 7C rather than the fair-use one.

Nothing else reads live OSM: `grep -rn "openstreetmap.org|overpass" apps/web/src`
returns only the attribution string in the map style credit.

### One place the code contradicts a decisions entry

D42 states that `qt` "is now in the query", having measured that quadtile
ordering is the difference between an answer and a timeout. The query builder
emits `out center tags;` — **without `qt`**
([geo/overpass.ts:143](../apps/api/src/geo/overpass.ts#L143)). The measurement
stands and the code did not follow it. Fixed under correction 7C rather than by
weakening the entry: a local instance is faster but not immune, and an ordering
that costs nothing to ask for should be asked for.
